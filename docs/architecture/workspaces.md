# 工作区设计讨论

更新日期：2026-11-03。

本文记录已确认并实现的工作区基础规则。业务资源模型仍随具体业务功能增加。

## 已确认规则

- 同一用户可以创建多个工作区，也可以加入多个工作区，跨工作区共用登录身份。
- 工作区是业务数据的归属与隔离边界。用户同时参与多个工作区，不会让这些工作区的成员互相获得业务数据访问权。
- 用户注册成功后，自动创建一个初始工作区；初始只有该用户，之后可以邀请其他用户加入。
- “私有”表示初始成员状态，不表示永久单人或不可协作的工作区类型。
- 第一版通过邀请并接受邀请加入工作区，不包括公开搜索加入、申请审批或按邮箱域自动加入。
- 工作区采用 owner / admin / member 三种固定角色，暂不提供自定义角色。创建者初始为 owner；owner 与 admin 管理工作区设置和成员；工作区删除及所有权转让仅由 owner 执行。业务资源的具体操作权限随业务功能确定。
- 邀请人填写受邀邮箱并生成邀请链接，自行复制发送；受邀者须使用对应邮箱登录并接受邀请。第一版不接入邮件投递。
- 工作区标识进入 URL，不同标签页可以独立操作不同工作区，切换互不影响。
- 工作区 ID 固定为 8 位小写字母与数字的组合，至少包含一个字母和一个数字；自动创建与手动创建统一由服务端生成。生成时按大小写不敏感规则检查现有 ID 和 slug，重复则重新生成，数据库主键与 slug 唯一约束防止重复落库。页面参数和激活接口将 ID 统一为小写。
- 用户确认目前没有已有账号，不增加历史账号补建或历史数据迁移流程。
- 手动创建工作区只要求填写名称，不要求公司信息或 Logo，暂不引入套餐配额。初始工作区使用“张三的工作区”这样的名称，之后可以修改。
- 正式页面右上角依次放置主题图标、语言图标、工作区切换下拉菜单，工作区切换器位于最右侧。
- 下拉菜单中的“管理工作区”进入当前工作区设置页，该页包含当前工作区信息、成员列表与创建工作区入口；邀请表单仅对 owner 和 admin 显示，API 同样限制这两个角色。
- 工作区设置是工作中心的第二个侧栏分组“设置”中的菜单项，进入设置页时保持工作中心选中。

### 工作区选择与登录

- 记录用户最后一次激活的工作区，供后续登录后的普通跳转使用。
- URL 带工作区标识时，以该标识为目标，不被最后激活的工作区覆盖。
- 登录后没有指定工作区目标时，进入用户最后激活的工作区；首次注册进入自动创建的初始工作区。
- 更新最后激活的工作区，只影响后续没有指定目标的入口，不改变其他标签页的 URL 或操作目标。
- URL 指定的工作区不存在或用户无权访问时，使用 Empty 显示“工作区不存在或无权访问”，工作区 Select 放在空态内容中；选择后点击“进入工作区”才进入目标，旁边保留创建按钮。仅该页不在右上角提供工作区选择，其他页面的切换位置与行为保持原样。
- 普通登录时，若最后激活的工作区已不可访问，则进入带工作区 Select 的入口页；没有任何可选工作区时自动弹出创建 Modal，创建成功后直接进入。空态始终保留创建按钮和收到的邀请入口。

### 邀请后的登录与加入

- 邀请链接是明确的登录返回目标，其优先级高于最后激活的工作区。
- 未登录用户从邀请链接发起登录后，先返回该邀请的确认页，接受后进入被邀请的工作区，并将其记录为最后激活的工作区。
- 首次注册的受邀者仍会自动获得自己的初始工作区，随后按邀请流程进入被邀请的工作区。

### 所有权、退出与删除

- 一个工作区允许多个 owner，存在期间至少保留一个。所有权不永久绑定创建者。
- 普通成员可以主动退出。最后一个 owner 退出前，须先让其他成员拥有 owner 身份。
- 初始工作区也允许删除，且允许用户删除最后一个工作区。
- 删除由 owner 操作，明确确认后删除工作区及其业务数据；第一版不提供回收站。
- 用户没有任何工作区时，进入“创建工作区／接受邀请”的页面，不自动重新创建工作区。

领域用语见 [GLOSSARY.md](../../GLOSSARY.md)。

### 界面组件与布局

- Hub 与 Agent 共用紧凑的吸顶顶部栏，高 48px，水平间距为移动端 12px、桌面端 16px，不显示底边框。顶部栏位于内容滚动容器内，背景渐变覆盖顶部栏并向下延伸 24px，从 `background` 色逐步过渡为透明，内容滚动时从其下方经过。
- 个人中心与工作区设置均使用 `max-w-4xl`（896px）的内容最大宽度，并统一水平对齐和顶部间距。
- `components/ui/modal.tsx` 提供受控 Modal，统一标题、描述、触发器和关闭行为；使用现有移动断点（小于 800px）切换为贴底 Drawer，桌面端使用 Dialog。
- 创建工作区通过 `CreateWorkspaceModal` 复用同一表单与 Modal；空态与设置页共用该入口。
- `components/ui/list.tsx` 提供语义化列表、行内容与操作区域；设置页以分区和分隔线组织信息，成员、邀请、退出与删除使用列表，不堆叠大卡片。
- 空态页顶部采用固定单行布局，账户、主题、语言为图标控件；Select 可以收缩，长名称截断，避免移动端换行和横向溢出。
- 个人中心位于 `/w/$workspaceId/account`，从当前工作区的账户菜单或工作中心侧栏的“设置”分组进入，共用工作区布局并高亮个人中心。页面展示头像、名称、邮箱、登录方式和注册时间，并提供主题和语言偏好；这些资料仍属于用户。有工作区时，通用入口 `/account` 跳转到最后激活工作区下的个人中心；无工作区时仍可通过该入口管理个人资料。
- 个人中心与工作区设置复用 `SettingsGroup`、`SettingsRow`；分区标题放在列表外，描述只属于具体列表项，不在卡片内部放置分区说明。背景复用系统 `muted` 色值。
- 个人名称与工作区名称在失焦或按 Enter 后自动保存；成功与失败通过现有 Toast 提示，失败可重试，不在输入框下保留保存状态。主题和语言选择立即生效。
- 邀请表单使用 `Group` 连接邮箱 Input 和角色 Select，提交按钮放在右侧；移动端保留单行，缩短按钮文字。

## 当前实现

- Web 使用无路径认证布局 `_a`；正式页面位于 `/w/$workspaceId/agent`、`/w/$workspaceId/hub/dashboard`、`/w/$workspaceId/settings` 与 `/w/$workspaceId/account`，使用语言 Cookie 选择界面语言。
- `/workspaces` 为普通登录入口，恢复最后激活的工作区；`/workspaces?choose=true` 为工作区选择及无目标时的创建／接受邀请入口。
- `/invite/$invitationId` 为邀请确认页；登录通过经过校验的 `next` 参数保留返回目标。
- API 的 Better Auth Organization 插件处理工作区、成员、角色和邀请；`databaseHooks.user.create.after` 创建初始工作区及 owner 成员关系。
- `GET /api/workspaces` 返回当前用户的成员工作区和最后激活的工作区；`POST /api/workspaces/:workspaceId/activate` 校验成员身份后更新激活记录。
- 组织、成员和邀请表由 `packages/db/src/schema/organization.ts` 定义；`user.lastWorkspaceId` 持久保存用户激活记录。Organization 插件所需的 `session.activeOrganizationId` 不作为页面目标来源。
- 数据库增量迁移由现有 Drizzle 脚本生成，仍需在目标环境通过 `make db-migrate` 或 `make db-migrate-remote` 应用。
- Agent 与概览页仍是业务占位页面；当前没有需要随工作区删除的业务资源表，成员与邀请由组织关系清理。后续新增业务表须实现工作区归属、授权及删除关联数据。

## 已确认技术方向

复用 Better Auth Organization 插件维护组织、成员、邀请及角色，产品中统一称为“工作区”。注册时创建的工作区与手动创建的工作区使用同一模型；选择理由见 [ADR 0001](../adr/0001-workspace-organization-model.md)。

URL 中的工作区是该页面的操作上下文，不使用共享会话中的当前组织选择来决定所有标签页的操作目标。页面挂载时记录激活，路由预加载不写入激活记录。插件提供的当前组织选择不能替代业务数据授权；后续业务接口仍需根据工作区、成员权限与资源归属限制访问。
