# 可移植的简历处理流程

招聘人员可以一次选择多份 PDF、JPEG 或 PNG，批次汇总进度，每份文件独立上传、处理和重试。客户端使用预签名地址将文件上传到私有 S3 兼容存储，然后调用业务 API。API 核对对象后逐份接受上传。工作区内相同文件可共享解析产物，每次上传仍有各自的记录。

文本提取消费者在调用模型前，对实际读取的原件字节计算 SHA-256。在同一工作区命中相同文件时，复用已完成的解析结果或跟随进行中的解析运行。

## OCR 阶段提取简历头像

OCR 队列消费者同时负责生成简历头像。PDF 仅用 PDFium 渲染第 1 页，JPEG 和 PNG 使用上传的图片。定位图的宽和高须各在 280 至 1568 像素之间，超出时先缩放，归一化坐标仍映射到原始图像。全文 OCR 读取完整原件。[Jev 图片尺寸限制](https://docs.typesafe.ai/images#limits)

通过 Vercel AI Gateway 调用 TypeSafe Jev 1.14。在同一次请求里判断页面是否含候选人真实照片，并取得以图像左上角为原点、范围为 0 到 1 的照片框。首版只采用存在概率至少 0.8 且定位置信度至少 0.5 的结果。JavaScript 按原图像素裁剪并输出长边不超过 512 像素的 PNG。头像定位输入只在内存中使用，裁剪结果通过 Files SDK 写入私有 R2。[Jev Box 接口](https://docs.typesafe.ai/primitives/box)

头像归属简历版本，R2 写入成功后才填充 `resume.avatarObjectKey`。已有头像继续复用。同一工作区重传已解析且缺少头像的原件时，可以在该次 OCR 消费中补齐头像。照片不存在、识别结果不满足采用条件，或者头像渲染、定位、裁剪或上传失败时，文本提取仍可完成并继续结构化。为限制 Worker 解码时的内存占用，头像裁剪处理至多 1200 万像素的 JPEG 或 600 万像素的 PNG。

## 阶段调度与重试

文本提取、结构化和岗位评价分别使用独立的队列，以便各自限流和积压。首版每个阶段最多同时执行六个任务，超出的任务留在各自的队列。工作流负责调度阶段及推进顺序，队列消费者执行对应阶段。业务代码依赖应用定义的对象存储、队列和工作流接口，Cloudflare R2、Queues 和 Workflows 通过适配层接入。

解析工作流在结构化完成后结束，待定岗状态由应用数据库保存。候选人和招聘岗位均确定后，启动独立的岗位评价工作流，使用当时的简历及岗位要求。更改匹配岗位时，自动结束原应聘并记录一条结束日志，在新岗位对应的应聘下自动发起一次新的评价。先前的评价仍归属原应聘。未来的自动岗位适配分析负责提出岗位，岗位确定后再启动该岗位的评价。

原应聘结束后，尚未调用模型的评价跳过。已发出的调用可以完成，结果留在原应聘的历史，原应聘维持已结束。

应用数据库保存处理进度和每次尝试，包括失败原因及当时的调用参数。工作流根据尝试结果决定是否发起新的业务重试，队列负责未确认消息的重新投递。消费者收到已记录结果的尝试时复用该结果。应用通过事务发件箱将业务状态和待投递消息在同一事务中保存，由转发任务交给队列或工作流。

消费者调用模型前在数据库中取得该次尝试的执行权并记录截止时间。工作流等候超时后先读取数据库，已有结果时按结果推进。仍无结果时记录本次中断，并在重试预算内发起下一次尝试。发件箱在事务提交后立即尝试派发，定时任务每分钟补发待投递记录。

每个阶段的自动重试预算为三次尝试，含首次调用。限流、超时、网络故障、上游服务错误和模型输出格式不合规可重试，默认分别等待 30 秒和 2 分钟，上游要求更长等待时采用该时长。损坏的 PDF 或凭据错误直接记录失败。手动重试从失败阶段继续，复用此前已保存的成功产物。

上传批次汇总文件上传与解析进度。各文件完成或失败后，批次展示成功与失败数量。待定岗和岗位评价进度分别在单份记录或相应应聘中展示。

阶段交接、数据记录和适配接口见[简历处理流程设计](../architecture/resume-processing.md)。
